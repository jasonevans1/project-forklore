# Task 003: Update Playwright quiz.spec.ts for the New Intro Screen

**Status**: completed
**Depends on**: 001
**Retry count**: 0

## Description
`tests/e2e/quiz.spec.ts` currently assumes `/quiz` drops straight into wizard step 1. After Task 001 gates the wizard behind an intro/"Start quiz" screen, almost every test in this file — which does `await page.goto('/quiz')` and immediately interacts with step-1 content — needs the intro dismissed first. Fix this with one shared-helper change rather than editing every test, then add a small number of new tests covering the intro screen itself.

## Context
- File to edit: `tests/e2e/quiz.spec.ts`
- Depends on Task 001 only — this file is independent of `QuizPageTest.php`/Task 002 and can run in parallel with it.
- Read the existing `resetQuizState()` helper (lines ~92-98) and its doc comment first. It already runs in `beforeEach` for both the desktop and mobile `describe` blocks (lines ~121-123, ~549-551) and calls the Livewire component's `restart` action directly via `window.Livewire.first().call('restart')`, bypassing the UI. `restart()` (per Task 001) sets `introDismissed = true` and persists session, but that alone isn't enough — most individual tests call `page.goto('/quiz')` *again* inside the test body (a real navigation, which remounts the component and re-reads `session('quiz.wizard')`). Since `restart()` also clears the session (`clearSession()`, unchanged, still asserted directly in Pest tests — do not touch that behavior), a fresh `page.goto('/quiz')` after `resetQuizState()` would show the intro screen again unless the session was re-persisted with `introDismissed = true` afterward.
- Fix: in `resetQuizState()`, immediately after the existing `restart` call/wait, add a second Livewire JS call to `startQuiz` (same `window.Livewire.first().call(...)` pattern, waiting on `waitForLivewire(page)` again) so the session snapshot left behind has `introDismissed: true`. This one change should make the entire existing suite pass again unmodified, since every test's in-body `page.goto('/quiz')` will now resume mid-session straight into `'questions'` state at step 1, exactly as before this plan.
- After that fix, add a few new tests covering the intro screen itself. **Gotcha — the `beforeEach` still runs for these tests too:** Playwright's `beforeEach` applies to every test in the `describe` block, and after the fix above it leaves the session with `introDismissed: true`, so a naive `page.goto('/quiz')` at the top of a new intro test resumes straight into the wizard and never shows the intro. To observe a genuinely fresh intro you must clear the persisted session *inside the test, after `beforeEach`*, before navigating. The least invasive way (mirroring how `resetQuizState` already drives the component): call `restart` on its own — `await page.evaluate(() => (window as any).Livewire.first().call('restart'))` (which calls `clearSession()` and forgets `quiz.wizard`) — and then WITHOUT a following `startQuiz`, `await page.goto('/quiz')`. The remount reads a null snapshot, so `introDismissed` falls back to its `false` default and the intro renders. Assert the "Start quiz" button is visible, then click it and assert the wizard step-1 content appears.
- If even that proves flaky under the serial/shared-session architecture, it is acceptable to assert the intro screen's presence/behavior via a component-level Livewire call sequence (mirroring how `resetQuizState` already interacts with the component) rather than a full session reset — prioritize keeping the diff small over exhaustive coverage here, per the codebase's existing e2e patterns in this file.
- Mirror the file's existing conventions: `waitForLivewire(page)` around any action that triggers a Livewire round-trip, `page.getByRole('button', { name: ... })` / `page.getByText(...)` selectors, and the `test.describe.configure({ mode: 'serial' })` shared-session constraint already documented in the file's comments.

- Pre-existing flakiness (unrelated to this diff): running the full file without a `--project` filter, or a single project with its default parallel workers, occasionally races the two serial `describe` blocks (`guided quiz` and `guided quiz — mobile`) against each other because both share the same `storageState` auth cookie and thus the same server-side `quiz.wizard` session, but Playwright's `serial` mode only serializes tests *within* one describe block, not across blocks/projects running on separate workers concurrently. This is the same architectural constraint already documented in the file's own comments (lines ~112-119) for within-block races; it just isn't fully closed for cross-block/cross-project races. Running with `--workers=1` (or one project at a time) makes the suite fully deterministic — verified twice for both `chromium` and `mobile` projects, 37/37 passing each time. Did not attempt to fix this pre-existing race since it's out of scope for this task and predates the intro-screen change.
